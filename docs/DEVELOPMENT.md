# Разработка Kebuz Launcher

Технические заметки о сборке, каталоге игр и подготовке исходников.
Все команды ниже выполняются из корня проекта `KebuzLoncher`.

## Сборка

Нужны Visual Studio 2022 или Build Tools с .NET desktop build tools,
.NET Framework 4.7.2 Targeting Pack и NuGet CLI. Из этой папки:

```powershell
nuget restore packages.config -PackagesDirectory ../packages
msbuild KebuzLoncher.csproj /p:Configuration=Release
```

`packages` должен лежать рядом с каталогом проекта. Можно открыть `.csproj`
в Visual Studio; общий `.sln` с Publisher для сборки лаунчера не нужен.
Результат: `bin/Release/KebuzLoncher.exe`. Зависимости встраиваются через Costura.
Поставка состоит из одного EXE. Лицензии и уведомления встроены в него
и доступны через пункт меню **Лицензии**.

Авторская иконка `KebuzLoncher.ico` входит в исходники и встраивается в EXE.
Без этого файла сборка останавливается, чтобы не выпустить приложение без иконки.

## Пользовательские данные

Настройки, установленные версии, кэш и резервные копии находятся в
`%LocalAppData%/Kebuz/KebuzLoncher/`. Обычные журналы пишутся в `logs`,
отчёты об ошибках в `logs/crashes`. Рядом с EXE данные не создаются.

При первом запуске отсутствующие файлы копируются из прежней папки
`%LocalAppData%/KebuzLoncher/`. Прежние файлы сохраняются; существующие файлы
в новой папке имеют приоритет и не перезаписываются. Маркер завершения
создаётся только после успешного копирования. Неудачный перенос можно повторить.

## Каталог и версии

В одном репозитории используются две ветки:
`main` для исходников и документации,
`catalog` для актуальных `config.json` и `manifest.json`. Релизы и теги общие.
Адреса заданы в `LauncherFeeds.cs`. Каталог загружается из
`https://raw.githubusercontent.com/Kebuzya/KebuzLoncher/catalog/config.json`,
а сведения об обновлениях отдельно из
`https://raw.githubusercontent.com/Kebuzya/KebuzLoncher/catalog/manifest.json`.
Запросы выполняются независимо и имеют отдельные файлы кэша.
Если файлы недоступны или повреждены, используются отдельные офлайн-кэши.
Запросов к прежним файлам в `main` нет; пользователям требуется новый EXE.
При старте сразу показывается сохранённый каталог, затем обновляется по сети.
Превью кэшируются в `%LOCALAPPDATA%/Kebuz/KebuzLoncher/cache/thumbnails`:
одинаковые URL используют одну загрузку, до четырёх загрузок идут параллельно.
Заменяя изображение, меняйте URL, например добавляйте `?v=2`, либо используйте
«Инструменты → Очистить кэш изображений».

Текущая версия задаётся одной константой `LauncherVersion.Number`.
Она используется в метаданных EXE, заголовке окна и сравнении версий.
Поддерживаются стабильные числовые версии из 2–4 частей, необязательный `v`.
Например, `1.2`, `1.2.0` и `v1.2.0.0` равны; prerelease-суффиксы не принимаются.

Чтобы объявить обновление, после загрузки готовой сборки обновите два поля
в `catalog/manifest.json` (шаблон: `manifest.example.json` в корне проекта):

```json
"launcher_version": "1.3.0",
"launcher_download_url": "https://github.com/Kebuzya/KebuzLoncher/releases/tag/launcher-v1.3.0"
```

Уведомление — небольшая полоса под меню. Кнопка «Скачать» открывает HTTPS-ссылку
в браузере; установка выполняется пользователем. Закрытие запоминается в
`settings.json`: та же или более старая версия больше не показывается, в том
числе после перезапуска. Следующая более новая версия снова покажет полосу.
Проверка идёт при запуске и обновлении списка; без модальных уведомлений.
При отсутствии версии или корректной HTTPS-ссылки уведомление не показывается.

В Publisher укажите ветку `catalog` и путь `config.json` после создания ветки
на GitHub. Старые локальные настройки автоматически не переключаются.
Publisher обновляет только `catalog/config.json`, без копирования в `main`.
`catalog/manifest.json` при публикации модпака или редактировании игр не меняется.
Этот файл обновляется отдельно после выпуска проверенного EXE лаунчера.
Порядок перехода описан в [RELEASING.md](../RELEASING.md).

## Предупреждения о совместимости модпаков

Запись игры в `catalog/config.json` может содержать необязательные поля:

```json
"mod_pack_status": "outdated",
"mod_pack_warning": "После обновления игры возможны ошибки. Сборка ожидает проверки."
```

Значения `mod_pack_status`: `unverified` (совместимость не проверена), `outdated`
(сборка может быть неактуальна), `broken` (известны проблемы). Отсутствие поля, пустая
строка или `none` скрывают предупреждение и не означают подтверждённую совместимость.
Неизвестное непустое значение отображается как непроверенная совместимость.

На карточке показывается только название проблемы, без увеличения высоты плитки.
Пояснение появляется при наведении на название и доступно в информации об игре.
Пояснение необязательно: без него используется стандартный текст из RU/EN ресурсов.
Авторский текст каталога показывается как есть. Предупреждение не блокирует установку
или запуск. Оно сохраняется в офлайн-кэше вместе с каталогом; обновление доступно после
повторной загрузки каталога. Старые клиенты игнорируют новые поля.

Пометку можно изменить через редактор каталога в приватном Publisher без публикации
архива. Новая сборка или патч не сбрасывают её: после проверки совместимости пометку
нужно снять вручную.

## Подготовка исходников

```powershell
powershell -ExecutionPolicy Bypass -File tools/Export-Source.ps1
```

Скрипт создаёт `../.artifacts/KebuzLoncher/KebuzLoncher-source.zip` из явного списка исходников,
документации и лицензий. Он не создаёт Git-репозиторий, не загружает файлы в сеть
и не изменяет локальные секреты. Publisher, родительский `.sln`, `token.txt`,
локальные конфиги, `.pfx`, `.csproj.user`, `bin`, `obj` и NuGet-пакеты
в архив не входят. Проверяется отсутствие типичных форматов токенов и ключей.
Автоматическая проверка не заменяет просмотр подготовленного архива.

Лицензия MIT подготовлена для собственного кода лаунчера. Перед публикацией
проверьте право лицензировать существующий код и имя правообладателя в LICENSE.
Зависимости разрешают распространение под MIT с сохранением их уведомлений.
Известные ограничения ресурсов описаны в [сторонних компонентах](../THIRD-PARTY-NOTICES.md).

## Релизы модпаков

В том же репозитории можно публиковать код лаунчера и ZIP-модпаки как вложения
отдельных релизов: `launcher-v1.2.0`, `modpack-repo-2026.05.03.2` и т. п.
ZIP загружается как release asset, в Git его коммитить не нужно.
В `mod_pack_url` указывается прямая ссылка на это вложение.
Отдельный тег маркирует коммит исходников, а архив прикрепляется к релизу.
По [правилам GitHub](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)
каждое вложение должно быть меньше 2 GiB.

Релизы модпаков помечайте `make_latest: "false"`; Latest оставляйте лаунчеру.
Проверка обновлений использует отдельный манифест, поэтому релиз модпака
не принимается за новую версию программы. Текущий локальный Publisher использует
изменяемые теги `{gameId}-latest` и при полном обновлении удаляет старые вложения:
для истории отдельных версий создавайте отдельные теги вручную или доработайте
Publisher. Для его изменяемых релизов не включайте GitHub Release Immutability.

Лицензии архивов модпаков указывайте отдельно в описании релиза и внутри ZIP.
MIT лаунчера не даёт разрешения распространять чужие моды или игровые файлы.
